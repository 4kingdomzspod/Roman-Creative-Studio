## Purpose

Define the security practices, controls, and policies that protect Roman Creative Studio's systems, data, team, and clients from unauthorized access, data loss, and cyber incidents.

**Business Value:** A security incident at a digital agency is existential. We hold client credentials, brand assets, and sometimes personal data. A breach doesn't just hurt us — it hurts every client we've served. Strong security is both a duty and a differentiator.

---

## Security Principles

1. **Least Privilege:** Every person and system gets only the access they need, nothing more.
2. **Defense in Depth:** Multiple layers of controls, not reliance on a single barrier.
3. **Zero Trust:** Verify identity before granting access, regardless of network location.
4. **Security by Default:** New tools and systems start secure; permissions are granted, not removed.
5. **Transparency:** Security incidents are reported honestly and promptly.
6. **No Security Theater:** Every control serves a real purpose; nothing exists just to appear secure.

## Access Control

### Account Provisioning
- Every team member gets individual accounts — no shared logins
- Accounts provisioned before first day (see Onboarding.md)
- Access level set at minimum needed for the role
- Access reviewed quarterly (access audit)

### Account Deprovision
- All access revoked within 4 hours of departure (see Offboarding.md)

## Password Policy

### Requirements
- Minimum length: 16 characters
- Must include: uppercase, lowercase, number, special character
- Must be unique per service (never reused)
- Must be generated by password manager (not manually created)
- No password hints stored anywhere

### Password Manager
**Tool:** 1Password Teams (or Bitwarden for Teams)
- All team members required to use password manager
- All business credentials stored in password manager only
- Never in: email, Slack, Notion, spreadsheets, or sticky notes
- Emergency access: 1Password Emergency Kit stored in secure physical location

### Password Rotation
- Critical systems (Stripe, Supabase prod, domain registrar): every 90 days
- Standard systems: annually or on team member departure
- Immediately: any system where credentials may have been exposed

## Multi-Factor Authentication (MFA)

### MFA Required (no exceptions)
- Google Workspace (email, calendar, Drive)
- GitHub
- Supabase
- Vercel
- Stripe
- Domain registrar (Namecheap, GoDaddy, etc.)
- Password manager
- Cloudflare (if used)
- Any system with admin access

### MFA Required (for admin/elevated access)
- Notion
- MailerLite
- Zapier
- Any new SaaS tool with admin role

### MFA Method Priority
1. Hardware security key (YubiKey) — highest security, required for CEO and CISO
2. Authenticator app (Google Authenticator, Authy) — required for all team
3. SMS — only if no authenticator app option available (least preferred)

### MFA Recovery Codes
- Stored in password manager, encrypted
- Never stored in email or chat
- CEO holds recovery codes for all critical systems

## Secrets Management

### Types of Secrets
- API keys (Stripe, Anthropic, SendGrid, etc.)
- Database connection strings
- OAuth client secrets
- Environment variables
- SSH keys
- SSL/TLS private keys

### Rules
- **Never** commit secrets to Git (even private repos)
- **Never** share secrets in Slack, email, or Notion
- Use `.env` files locally (in `.gitignore`)
- Production secrets: Vercel environment variables or Supabase vault
- Staging secrets: Separate set from production (never use production secrets in staging)

### Secret Rotation
- Rotate all API keys when a team member leaves
- Rotate immediately if any secret is accidentally exposed
- Annual rotation of all long-lived secrets (document in rotation log)

### If a Secret Is Accidentally Committed to Git
1. Immediately revoke/rotate the exposed secret (before anything else)
2. Remove from git history (git-filter-repo or BFG Repo Cleaner)
3. Assume the secret was compromised (even in private repos)
4. Notify CEO and CTO within 1 hour
5. Document in incident log

## Device Security

### Required on All Work Devices
- Full disk encryption enabled (FileVault on Mac, BitLocker on Windows)
- Lock screen after 5 minutes of inactivity
- Screen lock password required
- Automatic security updates enabled
- Antivirus / endpoint protection (Malwarebytes or equivalent)
- VPN available for use on untrusted networks

### Prohibited
- Work on personal devices without approved security setup
- Public WiFi without VPN
- USB drives from unknown sources
- Software from unofficial sources
- Disabling security features

### Mobile Device Policy
- Work email and communication apps on personal phones: encrypted device required
- PIN/biometric lock required on all devices with work access
- Remote wipe capability enabled (Find My / Google Find My Device)

### Lost or Stolen Device
1. Report immediately to CEO + CISO
2. Remote wipe the device
3. Rotate all credentials that were accessible on the device
4. Document in incident log
5. File police report if theft

## Source Control Security

### GitHub Organization Security
- Organization-level MFA enforcement: required for all members
- Default repository visibility: Private
- Branch protection on main/production branches:
  - [ ] Require pull request before merging
  - [ ] Require at least 1 approval
  - [ ] Require status checks to pass
  - [ ] Prevent force push
  - [ ] Prevent deletion
- GitHub Actions secrets: stored as encrypted secrets, never in code
- Dependency scanning: GitHub Dependabot alerts enabled
- Secret scanning: GitHub secret scanning enabled on all repos

### Code Review Security Standards
- No credentials in code (automated detection via GitHub secret scanning)
- Dependencies audited before adding to production: check npm audit
- No `eval()` or unsafe patterns without security review
- SQL queries use parameterized statements (no string concatenation)
- User input sanitized before use

## Incident Response

### Incident Severity Levels

| Level | Definition | Examples | Response Time |
|-------|-----------|---------|---------------|
| P1 Critical | Active breach; data exfiltration | Ransomware; account takeover | Immediate (24/7) |
| P2 High | Potential breach; systems compromised | Suspicious access; secret exposed | <2 hours |
| P3 Medium | Security control failure | MFA disabled; password policy violated | <24 hours |
| P4 Low | Policy non-compliance | Weak password found | <72 hours |

### Incident Response Process

**Phase 1: Detect & Contain (0–30 min)**
1. Identify the incident type and scope
2. Isolate affected systems immediately
3. Preserve evidence (don't wipe or shut down without instructions)
4. Notify CEO + CISO immediately

**Phase 2: Assess (30 min–2 hours)**
1. What data or systems were affected?
2. Was client data involved?
3. Is the incident ongoing or contained?
4. What is the blast radius?

**Phase 3: Eradicate & Recover (2–24 hours)**
1. Remove threat (malware, unauthorized access)
2. Rotate all potentially compromised credentials
3. Restore from clean backup if needed
4. Verify systems are clean before resuming

**Phase 4: Communicate**
- Internal: CEO briefed at every phase
- Client notification: only after legal review if client data was involved
- Regulatory notification: GDPR 72-hour rule applies if EU data involved

**Phase 5: Post-Incident Review (within 7 days)**
1. Root cause analysis
2. What controls failed?
3. What would have prevented or detected this sooner?
4. Update security framework and training
5. Document in Incident Log
