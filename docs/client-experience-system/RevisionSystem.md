# Revision System
## Roman Creative Studio — Phase 6, Document 7

---

### Why Revision Control Matters

Uncontrolled revisions are the primary cause of:
- Projects running over budget
- Projects running over timeline
- Client dissatisfaction (paradoxically — too many revision rounds often produce a worse outcome as direction becomes fragmented)
- Scope creep that erodes profitability
- Designer/developer burnout

The revision system doesn't limit creativity — it structures it. Defined rounds with consolidated feedback actually produce better outputs because feedback is gathered thoughtfully rather than reactively.

---

## Section 1 — Revision Definitions

### What Counts as a Revision

A revision is any change to work that has already been delivered and reviewed:

- Changing a color, font size, or spacing
- Rewriting a headline or body copy
- Moving a section to a different position
- Replacing an image
- Adjusting a layout
- Adding a content element within an existing page

**One revision round = one consolidated list of changes submitted together.** Submitting 3 separate emails with changes each counts as 3 revision rounds, not 1.

### What Does NOT Count as a Revision

| Item | Reason |
|---|---|
| Fixing a bug (broken link, form not submitting, rendering error) | Bug fixes are not revisions — they are quality issues |
| Implementing approved strategy changes | If it was in the approved strategy doc, it's not a revision |
| Content swaps agreed at kickoff (swapping placeholder with real copy) | Part of the original build |
| SEO updates to titles and meta descriptions | Part of the development scope if in contract |

## Section 3 — Revision Submission Format

### Required Format for Client Feedback

All feedback must be submitted in the following format. Unstructured feedback ("I don't know, something just feels off") will be returned with a request for specifics before being implemented.

```
FEEDBACK SUBMISSION FORMAT

Project: [Name]
Phase: [Design / Staging]
Round: [1 / 2]
Date: [Date]

Item 1:
  Page:       [Page name — e.g., Homepage]
  Section:    [Section description — e.g., Hero]
  Change:     [Specific description — e.g., "Make the headline 4px larger"]

Item 2:
  Page:       [Page name]
  Section:    [Section description]
  Change:     [Specific description]

... (continue for all items)
```

**This format is provided to clients in the staging delivery email.** It is not something they need to discover — it is given to them with the template.

## Section 4 — Feedback Rules

### Rule 1: Consolidated Submission

All feedback for a given phase is submitted in a single document or email. RCS will not accept feedback dripped over multiple messages over multiple days.

**If additional feedback arrives after the round is in progress:**
```
"I'm currently implementing the feedback from [Date].
I'll add [new item] to the next revision round — or if it's time-sensitive,
let me know and I can include it as a change order."
```

### Rule 2: Specific Over Subjective

**RCS responds to actionable feedback:**
- ✓ "The testimonial section background feels too dark — can we try the surface color instead?"
- ✓ "The mobile navigation text is too small to read comfortably"
- ✓ "Can we move the FAQ section above the final CTA?"

**RCS does not respond to vague feedback:**
- ✗ "Something about this doesn't feel right"
- ✗ "I showed it to my team and they're not sure about it"
- ✗ "It's missing something but I can't put my finger on it"

For vague feedback, RCS responds:
```
"I want to make sure I address this correctly. Can you help me
be more specific? What is it about [section] that isn't landing
for you? Is it the color, the layout, the copy, or the image?"
```

### Rule 3: One Reviewer

Established at kickoff: one designated point of contact submits all feedback. If multiple stakeholders are reviewing, they consolidate internally before submitting to RCS.

**Why:** Multiple reviewers submitting separate feedback creates conflicting direction and revision loops that satisfy no one.

### Rule 4: No Style Reboots After Approval

If a client approved the design direction in Phase 4 and then in the staging review asks to "make it lighter" or "go in a completely different direction" — this is a new project phase, not a revision. It is handled as a change order.

**Response:**
```
"This is a significant direction change from the design we approved
on [date]. I can absolutely explore a different direction, but it
falls outside the revision scope of this project.

I'd handle it as a change order: [scope + cost + timeline impact].
Would you like me to put that together?"
```

## Section 5 — Revision Turnaround Times

| Phase | RCS Revision Turnaround (from feedback received) |
|---|---|
| Strategy document | 24–48 hours |
| Wireframes | 24–48 hours |
| UI Design revisions | 2–3 business days |

```
"Got your feedback — thank you for the clear notes. I'll have the
updated [design / staging] to you by [specific date]."
```

## Section 6 — Handling Difficult Revision Scenarios

### "My team has completely new feedback after I already approved it"

```
"I understand. Once a phase is approved and we've moved forward,
revisiting it is considered additional scope — it requires unwinding
work already completed.

I can put together a change order for what your team is requesting.
Alternatively, if it's minor adjustments rather than a direction change,
let's look at what we can address within the existing scope."
```

### "Can you just make a few small changes after launch?"

Post-launch adjustments fall into two categories:
- **Bug fixes** (something broken): covered in 30-day post-launch support
- **Content or design changes** (something you want different): handled via Care Plan or change order

```
"Happy to help. [Change description] is a content update — that falls
under your Care Plan if you're on one, or I can handle it as a small
change order. Which would you prefer?"
```
